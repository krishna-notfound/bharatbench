# Evaluation guide: claims, code, tests, how to verify

Each row is one claim the project makes. "Code" is where it is implemented (`path:line` at the time of writing;
if a line moved, search for the named symbol). "Test" is the pytest function that exercises it. "Verify" is a
command that runs offline unless stated. Commands run from the repo root; `A` = `cd api && uv run pytest -q`,
`H` = `cd harness && uv run pytest -q`.

Status vocabulary: **Tested** (a unit/integration test with mocks passes), **Reviewed** (code read, no automated
test), **Not verified on hardware** (needs the real device lab; see `docs/LIMITATIONS.md`).

## What an evaluator cannot verify offline

- Behaviour on a real redroid device (netem shaping, memory cap OOM kills, screencap) - the harness tests use a
  mocked `adb`/`tc`. See `docs/LIMITATIONS.md`.
- Live Sarvam STT/LLM/TTS output quality and latency (only the figures listed in `docs/METRICS.md` were observed).
- Supabase RLS behaviour (policies are in `supabase/migrations/*.sql`; the API tests use respx mocks).
